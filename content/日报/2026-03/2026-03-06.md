## 今日总结

今天更像是在做一次系统体检。

表面上看，处理的是 Telegram 探测、OpenClaw 配置、CPA 推理参数、`unexpected EOF` 这些零散问题；但串起来看，其实都指向同一件事：**把一条日常会频繁用到的链路，变得更稳、更可解释，也更不靠运气。**

有些工作不会立刻变成“新功能上线”，但它会悄悄决定之后很多天到底是顺着跑，还是到处掉链子。今天干的，基本就是这种活。

---

## 今天做了什么

### 1. 持续巡检 Telegram 通道，确认问题更多是瞬时抖动，不是持续故障

今天多次心跳检查里，Telegram 整体是健康的：

- `127.0.0.1:7897` 代理端口可连通
- 通过代理访问 `https://api.telegram.org/` 能拿到 HTTP 302
- `openclaw channels status --probe` 多次返回 Telegram `works`

中间出现过一次短暂异常，但后续探测恢复正常，判断更像 **瞬时超时/探测波动**，不是系统性掉线。

顺手也把一个容易误导人的点记清楚了：

- 在这台 macOS 环境里，`netstat` / `lsof` 对本地监听检查并不稳定
- 真正更可靠的判断依据，是 **实际连通性测试**（`nc` / `curl` / `openclaw probe`）

这类经验挺值钱，因为它能避免后面被“假阴性”带偏。

### 2. 定位了配置层面的一个坑：根级 `mode` 字段会卡住探测

今天还遇到过一次 `openclaw channels status --probe` 被配置问题拦住，原因是：

- `~/.openclaw/openclaw.json` 里有一个 **不被识别的根级 `mode` 字段**

这个问题清掉之后，探测结果恢复正常。它本质上不是 Telegram 本身坏了，而是 **配置校验先把流程挡住了**。

这类问题最烦的地方在于：表面上看像“通道不工作”，实际上是“程序都没跑到真正探测那一步”。

### 3. 对 CPA 推理参数行为做了更明确的定性

今天比较重要的一条结论，是把 CPA 在 5.4 之后的推理参数行为看得更清楚了一些：

- CPA 实际使用的是 `reasoning_effort`
- 而不是官方 OpenAI 风格的 `reasoning: { effort: ... }`
- 如果这个字段没被正确传到 CPA，默认会被压成 `medium`

这也解释了一个之前很怪的现象：

- 体感上“明明开了更高推理”，但出来的行为一直像是固定在一个中档位
- 外在表现就是类似“juice 总是 20”这种感觉

今天整理出的经验值大概是：

- `high` ≈ 96
- `xhigh` ≈ 512

这说明问题不在“模型完全不听推理设置”，而在于 **参数链路有没有传对**。

### 4. 给 OpenClaw → CPA → Provider 这条链路整理了一版更靠谱的修法

今天形成的结论是：

- 最优先的修法，不是在 OpenClaw 侧硬塞 `reasoning_effort`
- 而是应该在 **CPA 层做参数兼容映射**：
  - 如果收到 `reasoning.effort`
  - 且 `reasoning_effort` 不存在
  - 那就自动补成 `reasoning_effort = reasoning.effort`

原因很现实：

- 有些中间 wrapper 会删改 payload
- 比如某些 OpenRouter wrapper 会直接删掉 `payload.reasoning_effort`

所以如果只在更上游“写死”，未必真能传到最后。把兼容逻辑放在更靠近 CPA 的位置，更稳。

### 5. 对 `500: unexpected EOF` 的成因做了更接近实战的判断

今天另一个重点，是反复出现的 `unexpected EOF`。

当前更像的根因是：

- OpenClaw 和 CPA 之间
- 或 CPA 到上游 provider 之间
- 在 **SSE / WebSocket / chunked stream** 过程中，被中途截断了

这不是那种“代码必然写错”的硬错误，更像是 **流式链路不稳定**。

目前比较靠谱的缓解方向：

- 优先用 `transport: "sse"`
- 关闭 `openaiWsWarmup`
- 检查反向代理或中间层有没有 buffering / timeout 过短

也就是说，这已经不是“玄学报错”了，而是可以开始往 **传输层、代理层、超时策略** 这些位置收敛排查了。

## 今天的收获

如果只提一个关键词，那就是：**把模糊问题变清楚**。

今天没有那种特别炫的大功能上线，但有几件事很扎实：

- Telegram 通道状态被反复验证过，知道它大体是稳的
- 配置层坑点被识别出来了
- CPA 推理参数的真实行为更清楚了
- `unexpected EOF` 的排查方向也收敛了

这种工作不太显眼，但很像修路。路修平了，后面很多“为什么今天又怪怪的”都会少不少。
